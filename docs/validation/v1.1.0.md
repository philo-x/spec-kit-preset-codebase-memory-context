# v1.1.0 Tool-Neutral Refactoring and Spec Kit v1.1.2 Validation

Date: 2026-10-09

This validation report documents the refactoring of `speckit.codebase-memory`
to a tool-neutral evidence analysis workflow, aligned with the Spec Kit v1.1.2
baseline. The immutable historical records for v1.0.0 and v1.0.1 remain in their
respective files.

## Subject Under Test

- Preset: `codebase-memory-context` v1.1.0
- Spec Kit Baseline: Spec Kit v1.1.2
- Platform: macOS arm64, Python 3.14
- Backend Modes:
  - Base Mode: Direct filesystem reading, code search, and file enumeration (no graph backend)
  - Optional Enhancement Mode: `codebase-memory-mcp==0.10.8`

## Validation Scenarios and Results

### 1. Tool-Neutral Execution Path (No Graph Backend)

In an environment without MCP servers or the `codebase-memory-mcp` CLI executable:
- The command successfully executed its baseline discovery using repository
  reading and code search.
- Repository structure, primary modules, entry points, technology inventory,
  and validation commands were reliably identified.
- No graph project, index node count, or synthetic coverage metrics were
  fabricated. Section 5 accurately recorded the actual file and directory
  scopes inspected directly.
- The workflow completed and generated a valid `.specify/memory/codebase.md`
  adhering to `schema_version: "2.0"`.

### 2. Read-Only Project Setup Verification Boundaries

The pre-execution check was validated under strict read-only constraints:
- **Missing ignore files**: When tested in a project without `.gitignore` or
  `.dockerignore`, the command adopted a conservative analysis scope and
  recorded the scope boundaries. No ignore files were created or modified.
- **Sensitive data isolation**: Files containing private keys, credentials, and
  `.env` secret definitions were excluded from analysis. Only configuration
  keys and redacted representations were cited. Switching analysis tools to
  bypass sensitive file exclusions was strictly disallowed.
- **Path and symlink bounds**: Symlinks resolving outside the canonical
  repository root were rejected. Target context path resolution was verified
  to remain strictly within the repository boundaries.
- **Preservation of user work**: Tested with uncommitted modified files in the
  working directory. The generator completed without running `git reset`,
  `git clean`, or `git checkout`, leaving uncommitted work completely intact.

### 3. File Ownership and Manual Overrides Preservation

- **Byte-for-byte override preservation**: An existing context file with custom
  human notes in `<!-- PROJECT OVERRIDES START -->` ... `<!-- PROJECT OVERRIDES END -->`
  was refreshed. All content between the markers was preserved byte-for-byte.
- **Unowned file protection**: An existing `.specify/memory/codebase.md` lacking
  the `generator: "speckit.codebase-memory"` frontmatter marker was detected;
  the generator refused to overwrite the file and halted with clear guidance.
- **Malformed markers**: When tested with missing or mismatched override
  markers, the generator stopped without modifying the existing file.
- **`--replace-existing`**: When invoked with `--replace-existing`, the user's
  explicit replacement authority was honored, replacing the entire file
  with a freshly synthesized document while warning the user.

### 4. Lifecycle Hooks (`before_codebase_memory` / `after_codebase_memory`)

The custom lifecycle hooks were tested against `.specify/extensions.yml`:
- **Re-entrancy prevention**: Attempting to invoke `speckit.codebase-memory`
  from within a hook execution was intercepted and blocked.
- **Optional vs. mandatory hooks**: Optional hooks displayed invocation
  instructions without executing automatically. Mandatory hooks were executed
  and waited upon before proceeding.
- **Hook failure distinction**: When a post-execution hook failed after context
  synthesis, the completion report clearly reported that the context file had
  been refreshed, but post-execution validation had failed, preventing the
  workflow from claiming overall success. No unauthorized rollback occurred.
- **YAML parse errors**: Malformed `extensions.yml` resulted in a warning that
  hooks were unverified, continuing execution without claiming absence of hooks.

### 5. Downstream Consumer Workflows (Spec Kit v1.1.2 Alignment)

Each of the four core consumer commands was tested with and without context:
- **Missing context fallback**: When `.specify/memory/codebase.md` was absent,
  `speckit.plan`, `speckit.tasks`, `speckit.analyze`, and `speckit.implement`
  executed standard Spec Kit v1.1.2 workflows seamlessly without error or
  forced context generation.
- **Source of truth verification**: Downstream commands used context for
  orientation, but corroborated critical paths, dependency versions, and
  commands against current source files.
- **Uncertainty handling**: `Inferred` and `Unknown` conclusions in context were
  not promoted to settled facts during planning or task creation.
- **Architectural change tolerance**: Documented intentional architectural
  deviations were accommodated in planning with migration tasks, rather than
  being automatically rejected for diverging from historical conventions.

## CI Split Verification

The repository CI workflow was split into two independent jobs:
1. `test-base`: Runs across Python 3.11 and 3.13 in an environment without
   `codebase-memory-mcp`. Verifies preset manifests, templates, rendering,
   command structures, and file operations.
2. `test-optional-backend`: Runs with `codebase-memory-mcp==0.10.8` installed to
   verify optional backend compatibility and contracts.
